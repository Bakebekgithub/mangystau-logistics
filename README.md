# Mangystau Logistics

Диспетчер внутрирегиональных грузоперевозок Мангистауской области.

Кейс хакатона Mangystau: «Цифровая платформа грузоперевозок и последнего километра».

---

## Чем это отличается от биржи объявлений

Биржа сводит **одну заявку с одной машиной**. Заявка на 400 кг в село за 250 км на бирже
не получает отклика — отдельный рейс за такой груз убыточен, и заявка просто умирает.

Мы собираем **несколько заявок в один рейс**:

- **обратная загрузка** — машина не возвращается порожней;
- **консолидация** — мелкие грузы в отдалённые посёлки едут одним заходом.

Биржа сводит существующий спрос с существующим предложением. Диспетчер **создаёт перевозку,
которой не существовало**.

## Что считает движок

На текущем плане из 48 заявок и 18 машин:

| Метрика | Значение |
|---|---|
| Оплачиваемых километров | **86%** (арифметический потолок схемы «туда с грузом, обратно порожняком» — 50%) |
| Не поехали | **6 967 км** из 14 493 |
| Сэкономлено топлива | **1 460 л**, ≈ 489 000 ₸ |
| Мелких грузов (<1 т) дальше 100 км в село обслужено | **6** |

Три метрики приведены сознательно, от самой сильной к самой слабой:

1. **Доля оплачиваемого пробега** — чистая арифметика по собранному маршруту, оспорить нечем.
2. **Экономия против текущего состояния** — калибрована по цифре из кейса (порожний пробег в
   регионе ~40%), то есть по данным организаторов, а не по нашему допущению.
3. **Против отдельного рейса на каждую заявку** — верхняя граница, помечена как таковая.

Все допущения — цена дизеля, расход груженого и порожнего хода — вынесены в
[`lib/engine/economics.ts`](lib/engine/economics.ts) и выводятся на экран методологии.

## Что здесь настоящее, а что смоделировано

**Настоящее:**

- **65 населённых пунктов** Мангистауской области из OpenStreetMap: названия на казахском и
  русском, координаты, население ([`data/settlements.json`](data/settlements.json))
- **2080 расстояний** по дорожной сети через OSRM — ни одного по прямой
  ([`data/distance-matrix.json`](data/distance-matrix.json))
- Постоянная база данных Postgres, свой серверный бэкенд
- Алгоритм сборки рейсов и расчёт экономики

Побочная находка по региону: дороги Мангистау в среднем **на 53% длиннее прямой линии**
(коэффициент 1.533, измерен по 4158 маршрутам).

**Смоделировано:** кто именно что везёт, парк машин и их положение, движение по маршруту.
Реальных грузоотправителей у проекта нет. Спрос генерируется не случайно, а от населения и типа
пункта: города отправляют, отдалённые села получают, часть сёл отправляет обратно — именно это
и создаёт возможность обратной загрузки. Генератор детерминированный, поэтому демо каждый раз
показывает одну и ту же ситуацию.

## Требования кейса

| № | Требование | Как закрыто |
|---|---|---|
| 01 | Работающий прототип по ссылке | Next.js на Vercel |
| 02 | Реальный бэкенд + БД, без localStorage | API-роуты Next.js + Postgres (Neon) |
| 03 | Данные о Мангистау | 65 пунктов из OSM, 2080 дорожных расстояний из OSRM |
| 04 | Визуализация карты / трекинга | Leaflet: маршруты, грузопоток, движение |
| 05 | Демо ключевого сценария | заявка текстом → сборка рейса → приёмка водителем → трекинг |
| 06 | Экономическое обоснование | калькулятор на реальных расстояниях + экран методологии |

## Как запустить

Нужен Node 22+.

```bash
npm install

# 1. Справочные данные (уже лежат в data/, шаг нужен только для пересборки)
npm run data:settlements     # 65 пунктов из OSM через Overpass
npm run data:matrix          # 2080 дорожных расстояний через OSRM

# 2. База. Без DATABASE_URL поднимется локальный PGlite — это настоящий
#    Postgres в WebAssembly, тот же SQL, что и в облаке.
npm run db:seed

# 3. Планирование: собрать рейсы из пула заявок
node scripts/plan.ts

# 4. Приложение
npm run dev
```

С облачной базой:

```bash
cp .env.example .env.local   # вписать DATABASE_URL от Neon
npm run db:seed:remote
```

Разбор заявки из текста работает **без ключа** — на детерминированном разборщике по словарю
региона. С `ANTHROPIC_API_KEY` включается разбор через Claude, который устойчивее к необычным
формулировкам. Обе реализации соблюдают один контракт, и приложение показывает, какая из них
отработала.

## Архитектура

```
data/*.json ──► scripts/seed.ts ──► Postgres
                                      │
                           lib/db.ts (PGlite | Neon)
                                      │
                   ┌──────────────────┼──────────────────┐
             lib/engine/          app/api/*          app/(роли)/*
       matching, economics       REST-роуты        экраны, Leaflet
```

Движок — чистые функции над матрицей расстояний, без обращений к базе, поэтому тестируется
напрямую. Маршрут внутри рейса ищется полным перебором с отсечением по трём правилам: погрузка
раньше выгрузки, вес в пределах машины, ветка отбрасывается при превышении лучшего результата.
Для того числа заявок, которое водитель берёт за раз, это даёт точный оптимум за миллисекунды.

Расстояния считаются на этапе сборки данных и кладутся в базу: во время работы приложение
не обращается к внешним сервисам, поэтому демо не зависит от чужого сервера.
